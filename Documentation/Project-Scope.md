
# ChildServe – QA Automation Project

## 1. Project Overview

This is a healthcare application testing portfolio project designed to demonstrate practical Quality Assurance and Automation Testing skills.

The project uses the OpenEMR demo application as the Application Under Test (AUT).

Application URL: https://demo.openemr.io/openemr

Note: This is an independent training project and is not affiliated with the actual ChildServe organization.

## 2. Project Objectives

- Validate application functionality.
- Identify and report defects.
- Perform positive and negative testing.
- Develop reusable UI automation scripts.
- Perform API testing.
- Validate database-related scenarios using SQL practice.
- Execute regression and cross-browser testing.
- Integrate automation with CI/CD.

## 3. Application Under Test

Application: OpenEMR Demo

Domain: Healthcare Management System

Testing Approach:
- Manual Testing
- Functional Testing
- UI Automation Testing
- API Testing
- Database Testing
- Regression Testing

## 4. In-Scope Testing

The following areas are planned for testing, subject to availability and verification in the demo application:

- Application Login and Logout
- Patient Search
- Patient Registration
- Patient Information Management
- Appointment Management
- User Interface Validation
- Form Field Validation
- Positive and Negative Scenarios
- API Validation
- Role-Based Access Testing

## 5. Out-of-Scope Testing

- Production healthcare systems
- Real patient information
- Real medical transactions
- Actual insurance claims
- Production database modifications
- Destructive testing on shared demo data
- Features not available in the demo environment

## 6. Test Environment

Operating System: Windows 11

IDE: Visual Studio Code

Automation Tool: Playwright

Programming Language: TypeScript

Runtime: Node.js

Version Control: Git and GitHub

Browser Coverage: Chromium, Firefox and WebKit (subject to support)

Application: OpenEMR Demo

## 7. Risks and Assumptions

- Demo application data may change or reset.
- Shared demo users may modify application data.
- Some features may not be available.
- Network connectivity may affect test execution.
- Only synthetic test data will be used.
- No real patient information will be stored or published.

## 8. Entry Criteria

- Application is accessible.
- Test environment is available.
- Testing requirements are documented.
- Test data is prepared.
- Required tools are installed.

## 9. Exit Criteria

- Planned test cases are executed.
- Critical defects are documented.
- Automation scripts are executed.
- Test results are reviewed.
- Test execution report is prepared.
